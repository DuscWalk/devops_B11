## 6. 核心代码对应关系

| 函数 | 输入 | 输出 | 本次证据 |
|---|---|---|---|
| `instructions` | Dockerfile 文本 | 合并续行后的逻辑指令 | 候选校验依赖 |
| `prepare_candidate` | 初始 Dockerfile、候选 | 校验 FROM/单阶段/指令顺序，返回基线文本 | 候选通过，`candidate_sha256` 固定 |
| `classify_failure` | 构建日志 | `MISSING_MAKE` / `INFRASTRUCTURE` / `OTHER_BUILD_ERROR` | 第一轮判定 `MISSING_MAKE` |
| `execute` | 命令、日志路径、超时 | 退出码与完整输出 | 两轮构建与运行日志 |
| `auto_build` | 项目、候选、输出、期望、预算 | 两轮构建 + 验证 + `result.json` | `result.json` `SUCCEEDED` |

为什么第一轮必须到达缺 `make`：基线文件写裸 tag `python:3.13-slim`；构建前 `prepare_candidate` 会把候选的 digest 注入第一轮，因此两次构建实际都从 `python:3.13-slim@sha256:70729b46…`（同一镜像）派生，差异仅剩候选新增的依赖安装（见 `iter-01/Dockerfile`）。该镜像不含 `make`，`RUN make` 在 shell 层直接返回 127，日志出现 `make: not found`，只有该失败才被归类为 `MISSING_MAKE`，网络类错误不计。

第二轮如何产生最终镜像：候选在 `FROM` 固定 digest 的基础上新增安装 `build-essential` 的 `RUN`，`RUN make` 成功编译出 `hello`，构建产出 `sha256:ad96eb…`。

运行检查如何使用同一镜像 ID：`image-inspect.json` 取 `[0].Id`，与该轮 `attempts[1].image_id` 比对后，直接以该 ID 作为 `docker run` 的参数，禁用网络运行，验证程序行为与构建产物一致。
