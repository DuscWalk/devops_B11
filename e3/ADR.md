# E3 决策记录

## ADR-E3-001：在原仓新增阶段目录

问题：E2 已有正式提交、模块和成员历史，E3 需要继续开发。选择：`docs/` 归档课件，`e3/` 放当前要求与公共验收，不覆盖 E2。替代：新仓库或改写 E2。代价：阶段索引需维护，但能追溯原成果。

## ADR-E3-002：预期和观察分开

问题：人工参考答案容易被误报为检测器/自动修复结果。选择：fixture 明示 `B11_REFERENCE_ORACLE`，运行记录放独立新目录；现有原型结果另列。替代：把成功示例 JSON 当实际日志。代价：多一份清单，但便于核验来源和能力边界。

## ADR-E3-003：本地与 Docker 分别验收

问题：组员可能没有 Docker 或网络。选择：本地入口可离线验收核心行为，Docker 单独记录失败/成功；网络失败不能算预设工具链故障。替代：全流程强制依赖 Docker 下载。代价：本地通过只代表宿主环境，不能替代容器证据。

## ADR-E3-004：环境哈希先作为可验证提案

问题：E2 留有哈希语义但未定算法，主机 GCC 与旧 fzy 镜像不同。选择：按实际执行环境生成规范化 identity/hash，明确 B11 未经配对确认；不改公共契约。替代：填造固定值或套用旧配置名。代价：联调前仍需共同确认，宿主指纹不是完整环境证明。

## ADR-E3-005：新运行与有限导出

问题：clean/补丁及提交大型工作目录可能破坏源码或仓库。选择：仅在自己的 `e3/work/` 副本运行，目录不覆盖；仅导出日志/元数据/小型补丁，提交时检查摘要。替代：在原 fixture 直接构建或提交镜像归档。代价：工作目录会占用本地空间，需按目录单独清理。
